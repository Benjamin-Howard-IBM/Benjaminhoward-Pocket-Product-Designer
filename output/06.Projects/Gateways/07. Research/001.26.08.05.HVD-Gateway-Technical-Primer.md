# HVD Gateway - Technical Primer

**Created:** August 2026
**Author:** Benjamin Howard
**Purpose:** Domain onboarding - technical concepts for Gateway explained for a designer new to the space

---

## What Problem Gateway Solves

HashiCorp Vault is a secrets management tool. It stores sensitive things - API keys, passwords, certificates, database credentials - and hands them out to applications that need them.

When a company uses **HCP Vault** (the cloud-hosted, managed version), Vault lives in HashiCorp's cloud infrastructure. But the applications that need secrets from Vault live in the company's own private network - their AWS VPC, their Azure VNet, their data center.

**The problem:** How does an application in a private network reach a Vault that lives in someone else's cloud, securely, without punching a hole in their firewall?

The naive answer is: open an inbound port on the customer's network so Vault can reach in. But security teams hate this. Opening inbound ports is an attack surface. Regulated industries (banking, government, healthcare) often prohibit it entirely.

**Gateway solves this by flipping the direction.** Instead of Vault reaching into the customer's network, the customer deploys a small piece of software (the Gateway agent) inside their network. That agent reaches out to HCP Vault and establishes a secure tunnel. Outbound connections are almost always allowed. The customer never has to open an inbound port.

---

## The Tunnel - WireGuard

The secure connection between the Gateway agent and HCP Vault is built using **WireGuard** (pending IBM legal approval - if that falls through, an equivalent technology is used).

WireGuard is a modern VPN protocol. Think of it as a private encrypted pipe between two points. Traffic goes in one end, travels through the pipe, comes out the other end - and nothing outside the pipe can read it.

**Important for design:** WireGuard is invisible to the user. They don't configure it directly. Gateway abstracts it. The user experience is "create a gateway, connect it to your network" - not "configure a WireGuard peer with a public key and allowed IPs."

---

## The Gateway Agent - What the Customer Actually Deploys

The customer downloads a Gateway agent and runs it inside their network. It is a piece of software that:

1. Boots up inside the customer's environment
2. Reaches out to HCP and establishes the encrypted tunnel
3. Stays running, forwarding traffic between the customer's apps and Vault

The agent is distributed as:

- A **binary** (a single executable file - a compiled Go program) - preferred by security teams because it has no external dependencies
- A **Docker image** (a containerized version) - preferred by teams already running container platforms

Both options are required. The precedent is the **Terraform Cloud Agent** - a product HashiCorp already ships that works the same way. Gateway follows that same lifecycle model, including:

- Signed artifacts
- Optional self-updating binary
- Clear versioning and upgrade controls
- Auto-update configurable, not enforced

## Fan-In - Many Networks, One Vault

Large enterprises don't have one network. They have hundreds. A bank might have:

- 50+ AWS VPCs across different business units
- Azure VNets for certain teams
- On-prem data centers
- Acquired company networks

All of those networks might need to reach the same HCP Vault cluster.

**Fan-in** means many customer networks connecting into one Vault. Each network runs its own Gateway agent and establishes its own tunnel. Vault sees multiple tunnels all coming in.

The design challenge here is **peer limits** - there is a ceiling on how many simultaneous tunnel connections one Gateway can handle before it causes problems (security group explosion, routing table limits, operational instability). This ceiling needs to be documented explicitly in the UI, not discovered silently when things break.

For very large enterprises, the pattern is **multi-gateway topologies** - multiple Gateway instances running in parallel, each handling a subset of networks. This is a documented pattern customers need guidance on in the product itself.

## Source IP Preservation - Why Security Teams Care

When an application makes a call to Vault through the Gateway tunnel, the request travels like this:

```
App (customer network) → Gateway agent → encrypted tunnel → HCP Vault
```

By the time the request arrives at Vault, the original IP address of the app can get lost - replaced by the Gateway's IP or the tunnel endpoint's IP. This is called **NAT** (Network Address Translation) - the tunnel rewrites the source address.

This matters because Vault keeps an **audit log** of every request - who asked for what secret, when, from where. If source IPs are lost, the "from where" in the audit log becomes useless. For security teams doing forensics ("which machine accessed the production database password at 3am?"), that is a serious problem.

**Source IP preservation** means designing the tunnel so the original app IP survives the journey and appears correctly in Vault's audit log.

**Design implication:** Treat this as a hard constraint until engineering confirms otherwise. It is not an implementation detail - it is a design-level constraint that must be surfaced at configuration time if it involves a tradeoff.

## HA and DR - Why They Are a GA Gate

**HA (High Availability)** means the Gateway does not have a single point of failure. If one Gateway agent crashes or one tunnel drops, traffic fails over automatically to a backup. Enterprise customers run production workloads through Vault - an outage means applications cannot get secrets, which means they cannot function.

**DR (Disaster Recovery)** goes further. If an entire environment goes down (a whole AWS region, a data center), there is a Gateway already running in the DR environment, and failover is automatic - not "the ops team rebuilds it in 4 hours," but automatic.

The memo is explicit: **Gateway cannot reach GA without HA and DR.** Regulated customers will see the product as incomplete and will not put it in production. PoC and Private Beta can ship without it. GA cannot.

**Design implication:** The GA setup flow must walk customers through configuring both primary and DR environments, not just one. This needs a dedicated journey map before wireframes are finalized.

## CSP-Agnostic - What That Actually Means

**CSP** = Cloud Service Provider (AWS, Azure, GCP).

Today, if a company wants private connectivity to a cloud service, they use that cloud's native feature:

- AWS has **AWS PrivateLink**
- Azure has **Azure Private Link**
- GCP has **Private Service Connect**

Each one works differently. Customers with multi-cloud environments have to set up and manage separate private connectivity for each cloud. It is operational complexity multiplied by the number of clouds.

**CSP-agnostic** means Gateway works the same way regardless of which cloud the customer is in. Deploy the same agent binary, same configuration, same tunnel - whether on AWS, Azure, GCP, or on-prem. HashiCorp manages the complexity on their side.

**How this relates to your other Q3 work:**

Gateway and Azure Private Link are different features serving different customer needs:

| Feature | Approach | Who uses it |
|---|---|---|
| Gateway | CSP-agnostic managed tunnel | Multi-cloud customers, on-prem customers, customers who want one consistent model |
| Azure Private Link | Native Azure integration | Azure-only or Azure-primary customers who want native cloud integration |

Some customers will use one, some will use the other, some will use both.

## Observability - What Customers Expect

Customers do not expect HashiCorp to collect logs from their environment. They do expect:

- Clear health signals from the HCP-managed side (is the tunnel up or down?)
- Actionable Vault-side errors when connectivity fails
- Clear failure attribution - when something breaks, is it the Gateway, Vault itself, or the customer's network?

The last point is critical for design. Generic "connection failed" errors are useless to an ops team at 2am. The UI must distinguish between:

- **Gateway problem** - the agent is down or misconfigured
- **Vault problem** - Vault is unreachable or returning errors
- **Network problem** - the tunnel is up but traffic is being dropped somewhere in the customer's network

## Explicit Non-Goals

The Gateway is not:

- A service mesh (that is Consul's job)
- A general-purpose networking or routing feature
- A solution for east-west traffic between customer networks
- A product that requires customers to understand tunnel internals
- A product with an opinionated deployment model (VM-only, K8s-only)

Keeping this scope tight is itself a design constraint. The UI should not expose networking complexity that Gateway is supposed to abstract away.

## Design Mapping - Technical Concepts to UI

| Technical concept | What it means for the UI |
|---|---|
| Gateway agent deployment | Onboarding/setup flow: download artifact, run it, verify connection |
| Binary vs Docker | Deployment model selector in setup flow; different instructions per path |
| Tunnel establishment | Connection status indicator - up, healthy, degraded, or down |
| Fan-in / peer limits | Scale guidance copy; error states when limits are approached |
| Source IP preservation | Constraint surfaced at configuration time, not a silent behavior |
| HA configuration | Setup step requiring a second Gateway instance to be configured |
| DR configuration | Setup step for the failover environment |
| Failure attribution | Error messages that tell the user whether the problem is Gateway, Vault, or their network |
| CSP-agnostic model | Single setup flow that does not branch by cloud provider |
| Auto-update | Version and update settings in the agent configuration UI |

## Key Terms Glossary

| Term | Plain meaning |
|---|---|
| HCP Vault | The cloud-hosted, managed version of HashiCorp Vault |
| Gateway agent | The software the customer installs in their network to create the tunnel |
| WireGuard | The encrypted tunnel protocol connecting the agent to HCP Vault |
| VPC / VNet | Virtual Private Cloud (AWS) / Virtual Network (Azure) - a customer's private network in the cloud |
| Inbound port | An opening in a firewall that allows outside traffic to come in - what Gateway eliminates the need for |
| NAT | Network Address Translation - the process that can cause source IPs to be lost in transit |
| Source IP | The original network address of the application making a Vault request |
| Audit log | Vault's record of every request: who, what, when, from where |
| Fan-in | Many customer networks connecting into one Vault cluster |
| Peer | A single network connection endpoint in the tunnel (one VPC, one VNet, one on-prem segment) |
| Peer limit | The maximum number of simultaneous tunnel connections one Gateway can handle |
| HA | High Availability - no single point of failure; automatic failover |
| DR | Disaster Recovery - automatic failover when an entire environment goes down |
| CSP | Cloud Service Provider - AWS, Azure, GCP |
| CSP-agnostic | Works the same way regardless of which cloud you are on |
| Binary | A single compiled executable file - no dependencies, preferred by security teams |
| Docker image | A containerized version of the agent - preferred by teams running container platforms |
| TF Cloud Agent | Terraform Cloud Agent - the HashiCorp precedent product that Gateway's lifecycle model mirrors |
